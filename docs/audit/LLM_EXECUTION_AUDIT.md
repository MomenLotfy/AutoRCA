# Response Validation

*Only applied in the legacy LLM path (`LLMAnalysisService`).*

1. **Schema Validation of Request** – `OpenAICompatibleLLMClient._validate_request` validates the `RCARequest` against `rca_request.schema.json` (lines 92‑98).
2. **HTTP Request / Response** – The client sends a POST to `<base_url>/chat/completions` and reads the response body (lines 74‑77).
3. **JSON Parsing** – Extracts `choices[0].message.content` and parses it as JSON (lines 80‑84).
4. **Final RCA Schema Validation** – `_validate_final_rca` loads `final_rca.schema.json` and runs `jsonschema.Draft7Validator` (lines 100‑107). Errors raise `LLMClientError`.
5. **Deterministic Validator** – `LLMAnalysisService.generate_validated` invokes `FinalRCAValidator.validate_or_raise` (line 19‑20 in `llm/service.py`). The validator checks hypothesis ID, confidence, cited evidence, severity, schema conformance, and generation‑option nullability.

**Error Handling Paths** (see `OpenAICompatibleLLMClient`):
- Missing env vars → `LLMClientError` raised during client init.
- HTTP errors / timeouts → `LLMClientError`.
- Malformed provider response → `LLMClientError`.
- Schema violations → `LLMClientError`.
- Validation mismatches → `FinalRCAValidationError` (raised by validator).

All errors propagate up to the caller; in `web_app.analyze_incident` they are caught and translated to a `400` response (lines 141‑143).

# Production Readiness

| Area | Observation | Recommendation |
|------|-------------|----------------|
| **Timeouts** | LLM client timeout is fixed at 60 s (`OpenAICompatibleLLMClient.__init__`). | Make timeout configurable per‑environment. |
| **Retries / Circuit Breaker** | No retry logic; a single failure aborts the request. | Add exponential back‑off and circuit‑breaker state to protect downstream LLM service. |
| **Rate Limiting** | Not implemented for LLM calls. | Respect provider rate limits; add client‑side throttling. |
| **Secret Rotation** | Secrets read at import time; process restart required for rotation. | Implement dynamic secret reload or signal‑based reload. |
| **Observability** | No metrics or tracing for LLM latency or errors. | Export latency and error counters to Prometheus; add structured logs. |
| **Deterministic Fallback** | The V1 endpoint already operates deterministically; the legacy endpoint falls back to `400` on LLM failure. | Consider exposing a deterministic‑only mode flag for the legacy endpoint. |
| **Cost Controls** | LLM calls could be costly; no cost‑monitoring guardrails. | Add usage quotas or cost‑alert hooks. |

# Recommended Next Steps

1. **Clarify Documentation** – Clearly state in the API docs that `/api/v1/investigations` is deterministic‑only and does not produce an LLM narrative.
2. **Feature Flag for LLM** – Introduce a runtime flag (e.g., `ENABLE_LLM_NARRATION`) that, when true, routes the request through the legacy LLM path (`/api/analyze`) or a new unified path.
3. **Add Retry & Circuit‑Breaker** – Wrap the HTTP call in `OpenAICompatibleLLMClient.generate` with exponential back‑off and a circuit‑breaker to avoid cascading failures.
4. **Expose Metrics** – Add Prometheus metrics for LLM request latency, success/failure counts, and credential reload events.
5. **Improve Test Coverage** – Add an integration test that uses a local HTTP mock server to simulate the LLM provider, exercising real request/response handling and timeout behavior.
6. **Security Review of Secrets** – Ensure environment variables for LLM credentials are loaded securely (e.g., from a secret manager) and support hot‑reload without process restart.
7. **Cost Monitoring** – Implement logging of token usage and cost estimation per request for budgeting purposes.
8. **Consider Fallback Narrative** – If LLM fails, optionally return a minimal deterministic narrative (e.g., a templated summary) instead of a hard error, improving user experience.
