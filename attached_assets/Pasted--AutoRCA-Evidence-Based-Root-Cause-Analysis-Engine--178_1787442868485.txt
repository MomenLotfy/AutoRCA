مهم جدًا:
لا تبدأ بإعادة تصميم المشروع، ولا تعيد كتابة الـ Core، ولا تغيّر الـ deterministic reasoning architecture الحالية لمجرد تحسينها.

الحالة الحالية المستقرة:
- Real Git Collector
- Real File Collector
- Real CLI
- Deterministic Pipeline
- RulesConfig
- RuleEngine
- ScoringEngine
- EvidenceBuilder
- RCARequestBuilder
- FinalRCAValidator
- JSON Schema validation
- Real Git repository + real traceback execution
- 57 tests passing
- Current stable milestone: v1.4.0-alpha

المبدأ الأساسي للمشروع:
LLM DOES NOT DECIDE THE ROOT CAUSE.

القرار يتم بالكامل بشكل deterministic:

Raw Inputs
→ Observations

→ Rule Engine
→ Hypotheses
→ Selected Root Cause

ثم فقط بعد اتخاذ القرار:

Selected Root Cause
→ RCARequestBuilder
→ Structured RCARequest
→ LLM
→ FinalRCA
→ FinalRCAValidator
→ Final Report

الهدف من هذه المرحلة هو تنفيذ 3 مراحل فقط وبشكل incremental:

### القاعدة الأهم

الـ LLM ممنوع تمامًا أن يستقبل raw logs أو raw traceback أو raw git diff بهدف اكتشاف Root Cause.

الـ LLM يجب أن يستقبل فقط RCARequest الذي بناه RCARequestBuilder.

يعني:

❌ ممنوع:

Raw traceback → LLM → Root Cause

❌ ممنوع:

Git diff → LLM → Root Cause

❌ ممنوع:

Raw logs + prompt → LLM → Root Cause

المسموح:

Deterministic Engine
→ Selected Hypothesis
→ RCARequest
→ LLM
→ Explanation / Fix

الـ LLM دوره:
1. شرح Root Cause بلغة مفهومة.
2. شرح الأدلة الموجودة في RCARequest.
3. اقتراح Fix مناسب.
4. يمكنه اقتراح خطوات remediation.
5. لا يستطيع تغيير hypothesis_id.
6. لا يستطيع تغيير confidence.
7. لا يستطيع تغيير cited_evidence_ids.
8. لا يستطيع تغيير resolved_severity.
9. لا يستطيع اختراع Evidence جديدة.
10. لا يستطيع اختيار Root Cause مختلفة.

FinalRCAValidator هو آخر بوابة قبل قبول مخرجات الـ LLM.

--------------------------------------------------
2. LLM Provider abstraction
--------------------------------------------------

لا تربط الـ Core مباشرة بمزود LLM واحد.

أنشئ abstraction بسيط مثل:

LLMClient

بواجهة واضحة، مثل:

generate(request: RCARequest) -> FinalRCA

أو equivalent مناسب للـ architecture الحالية.

الهدف:

Core
   ↓
LLMClient interface
   ↓
Provider implementation

بحيث يمكن لاحقًا استخدام:
- OpenAI
- Anthropic
- Gemini
- Local model

بدون تعديل الـ deterministic Core.

لا تضف abstraction مبالغ فيه.

نريد أبسط تصميم production-friendly.

--------------------------------------------------
3. Structured LLM output
--------------------------------------------------

الـ LLM يجب أن يرجع structured output مطابقًا لـ FinalRCA schema.

لا تعتمد على plain text parsing إذا كان من الممكن استخدام structured JSON output.

الـ response يجب أن يتم parsing + validation قبل تمريره للـ FinalRCAValidator.

إذا كانت مكتبة الـ LLM المستخدمة لا تدعم structured output بشكل مباشر، استخدم JSON response + schema validation مع Fail Fast.

ممنوع قبول malformed output.

--------------------------------------------------
4. Prompt design
--------------------------------------------------

اكتب system prompt واضح للـ LLM يشرح:

"You are the explanation layer of AutoRCA."

ووضح:

- Root Cause has already been determined by a deterministic rule engine.
- You MUST NOT determine a different root cause.
- You MUST NOT invent evidence.
- You MUST use only the supplied RCARequest.
- You MUST preserve hypothesis_id.
- You MUST preserve confidence.
- You MUST preserve cited_evidence_ids.
- You MUST preserve resolved_severity.
- Your role is explanation and remediation guidance only.

الـ prompt يجب أن يعكس فلسفة AutoRCA:

Deterministic Reasoning
≠
Generative Explanation

--------------------------------------------------
Scenario 2 — Missing Dependency
--------------------------------------------------

أنشئ repo تجريبي حقيقي.

مثال:

app.py يستورد package غير مثبتة:

import nonexistent_package

ثم شغل:

python3 app.py

وسجل الـ real traceback:

ModuleNotFoundError

استخدم هذا كـ real input.

إذا كان التصميم الحالي يتطلب dependency evidence من source معين، استخدم collector مناسب بدل اختراع input داخل الـ engine.

المطلوب أن يصل deterministic engine إلى:

Missing Dependency

ثم RCARequest

ثم LLM explanation

ثم FinalRCAValidator

ثم report.

لا تضف rule جديدة إلا إذا كانت موجودة في taxonomy/rules architecture أو كانت إضافة ضرورية ومتوافقة مع التصميم الحالي.

إذا كانت rule غير موجودة أصلًا، توقف وأبلغني قبل توسيع الـ Core.

--------------------------------------------------
Scenario 3 — Port Conflict
--------------------------------------------------

يمكن استخدام Python socket/server أو Docker إذا كان collector الحالي يدعم ذلك.

المطلوب استخراج real error مثل:

Address already in use

ثم:

Observation
→ Evidence
→ Rule Engine
→ Port Conflict
→ RCARequest
→ LLM
→ FinalRCA
→ Validator

مرة أخرى:

لا تغير architecture الحالية.
