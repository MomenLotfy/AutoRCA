AutoRCA

Evidence‑Based Root Cause Analysis Engine – turning noisy incidents into clear, actionable RCA reports.

Overview

AutoRCA is a deterministic, test‑driven engine that ingests raw incident artifacts (Git diffs, tracebacks, Docker logs, CI logs, and optional observability integrations) and produces a structured RCA report. The pipeline is split into three logical phases:

  1. Extraction – raw sources become Observations via a collection of pluggable Extractors.
  2. Evidence – observations are matched against classification_rules to generate Evidence objects.
  3. Reasoning – a rule engine scores hypotheses, builds a timeline, correlates incidents, and finally hands a JSON‑compatible FinalRCA to an LLM for a human‑readable explanation.

Who Benefits

The engine targets small‑to‑medium teams that run CI/CD pipelines and need a repeatable way to diagnose failures without hand‑crafting ad‑hoc scripts. Typical users include:

  • DevOps engineers looking for automated post‑mortems.
  • Platform reliability teams that must surface root causes across services.
  • Developers who want a deterministic back‑stop before involving an LLM.

Architecture

The system is deliberately modular – each phase lives in its own package, exposing a clear public API. Below is a Mermaid diagram that visualises the data‑flow.

Core Components

  • Collectors – GitCollector, FileCollector, KubernetesCollector, plus optional observability collectors (Elasticsearch, Prometheus, GitHub/GitLab). All inherit from BaseCollector and expose a collect_with_metadata method.
  • Extractors – registered in extractors/registry.py. Each extractor declares the sources it consumes (e.g., traceback, git_diff) and yields Observations.
  • Evidence Builder – matches observations against rules.config.json to emit structured evidence objects.
  • Engine – includes RuleEngine, ScoringEngine, TimelineEngine, CorrelationEngine, and RemediationEngine. They operate on pure data structures, guaranteeing deterministic output.
  • Pipeline – orchestrates the flow in pipeline.py. It also accepts optional incident‑window bounds to filter observations.
  • CLI – entry point cli/main.py for local runs; supports --llm flag to invoke an OpenAI‑compatible provider.
  • API Service – api/investigation_service.py validates HTTP payloads, runs the pipeline, and persists investigations via an in‑memory or PostgreSQL repository.

Key Features

  • Deterministic analysis – the same inputs always yield the same hypothesis, enabling reproducible post‑mortems.
  • Extensible collector system – plug in any REST endpoint (Kubernetes, Elasticsearch, Prometheus) without touching the core pipeline.
  • Fail‑fast validation – rules_config, taxonomy, and JSON schemas are validated at startup.
  • LLM‑optional – the engine can output a complete JSON report without an LLM, useful for CI environments.
  • Incident window filtering – optional start/end timestamps keep analysis focused on the relevant time slice.
  • Security‑first – URL validation blocks SSRF, secret‑masking removes credentials from persisted payloads.

Getting Started

CLI

pip install -r requirements.txt
python -m cli.main analyze \
  --repo /path/to/repo \
  --environment production \
  --traceback /path/to/traceback.txt \
  [--llm]

When --llm is omitted the output stops at FinalRCA JSON. To enable the LLM set the following environment variables:

export AUTORCA_LLM_PROVIDER=openai-compatible
export AUTORCA_LLM_MODEL=gpt-4
export AUTORCA_LLM_API_KEY=YOUR_KEY

API

POST /api/v1/investigations with a JSON payload matching api/serializers.py. The service returns the created investigation record.

Configuration

All runtime limits (max window, max result size, max timeout) are defined in collectors/integration_base.py. The rules.config.json file drives classification and weighting – add new failure types by editing the taxonomy and accompanying rules.

Technical Debt Highlights

See docs/TECHNICAL_DEBT.md for a full list. Briefly:

  • LLM integration is a thin wrapper – a full retry/back‑off strategy is pending.
  • External collector implementations (GitHub Actions API, Docker daemon, live Kubernetes client) are staged for future work.
  • Evidence deduplication is limited to a simple key; a more robust fingerprinting system is planned.
  • Schema validation for collector metadata currently lives in the service layer; moving it upstream would tighten contracts.

Contributing

All tests run with pytest -q. The project follows a strict Fail‑Fast philosophy – any malformed rule, taxonomy entry, or config aborts startup. Submit PRs against the main branch and ensure the full suite passes.

Performance & Scalability

The pipeline is deliberately I/O‑bounded; collectors stream JSON via urllib.request with a configurable timeout_seconds (default 5 s). The main bottleneck is the size of the raw payloads, limited by MAX_K8S_OBJECTS (200) and MAX_RESPONSE_BYTES (5 MiB). All heavy lifting runs in pure Python data structures, making it easy to parallelise by sharding sources across processes if needed.

Benchmarks on a typical 8 core VM with a 2 GB dataset run under 1 s for extraction, 0.5 s for evidence building, and <0.2 s for the scoring stage.

Extending Collectors

To add a new external integration, implement a subclass of BaseCollector that implements _list_*() helpers and respects the MAX_RESULT_SIZE and MAX_WINDOW_SECONDS contracts. Register the class in collectors/__init__.py and add a corresponding entry to VALID_SOURCES in extractors/registry.py. The collector must expose a collect_with_metadata() method returning an IntegrationResult with items (raw JSON strings) and metadata (timestamps, pagination info).

Testing Strategy

AutoRCA ships a full pytest suite (302 tests). Tests are categorized as:

  • Unit tests – isolated logic (e.g., _in_window, rule scoring).
  • Integration tests – mock external collectors via urllib.request.urlopen patches.
  • End‑to‑end smoke tests – run real_scenarios.py with and without the --llm flag.

CI runs the suite on Python 3.12 with coverage thresholds (90 %). Adding a new collector requires a dedicated fixture that returns a minimal JSON payload and a corresponding test in tests/test_phase2_*.py.
